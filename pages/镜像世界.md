镜像世界是游戏中的一个Bug，由于游戏对活跃区域管理的缺陷而诞生。 

此Bug可能会使当前游戏受到极其严重且通常不可逆的影响。 

## 简要

游戏在运行中只能加载一个区域大的世界，区域是大小固定的 512x512 个区块，所以出现了如下问题： 

镜像世界存在于已加载区块的 512n 个区块外，原理上这是由于计算结果绕回。 

已知区块长宽都为 512 像素，可以算出区域的长宽都为 262144。 

由于从区域中获取区块的计算结果绕回，使得镜像世界和已加载区块共用了同一套材料。 

  * 这也是为什么称为镜像世界，因为地形是共用的导致影响主世界就会影响镜像世界，反之同理。只不过镜像世界有很多东西不能正常运行。
  * 这里这个 262144 也被称为一个镜像世界的大小，其实就是区域的大小。



从以上信息得出如下算式可用于计算镜像世界位置： 

镜像世界区块坐标=原始区块坐标+262144n (n∈Z,n≠0)

## 实体复制与可能的规避

因为游戏运行中只能加载一个区域大的世界，所以当两个区块加载器相差的距离大于等于一个区域的时候，就会发生很多奇怪的Bug，这里面就包含了实体复制。 

实体复制是游戏错误的多次加载了同一个区块产生的现象。 

  * 因为游戏对于区块的加载卸载采用了类似懒加载的策略，只要位置不变就不会进行区块加载卸载的更新。
  * 所以当两个区块加载器距离恰好为 262144n 时，游戏因坐标绕回将两个位置误判为同一个已加载区块，从而避免了实体复制。 
    * 因此，想要触发实体复制不能让一次传送正好重叠到了镜像世界，需要偏移一点位置。
  * 这也是为什么在区块边界反复横跳可能会导致更多实体复制的原因，因为区块加载器发生了位置变化，所以游戏正在尝试更新区块。



已知这些东西会进行区块加载： 

  * [玩家](米纳.md)
  * 跟随玩家的摄像机
  * [三眼](三眼.md)
  * [小小蛆](小小蛆.md)
  * [星辰之子](太阳.md)
  * [新日](太阳.md)
  * [暗日](太阳.md)



其中玩家和摄像机肯定没法规避了，剩下五个都可以通过重启游戏的形式，让它们被卸载从而停止区块加载。这样你就可以前往更远的世界探索而不触发bug了。 

但是因为玩家和摄像机都能加载区块，所以当玩家进行超远的传送[[1]](#cite_note-1)时就会有一瞬间满足上述条件，从而导致实体复制。 

### 关于实体复制的警告

  * 如果你不小心传送了半个区域大的距离[[2]](#cite_note-2)，这通常会导致游戏崩溃，解决方法就是重启游戏。
  * 滥用实体复制可能会导致大量卡顿，比如大量的圣山传送门，大量的box2d发生碰撞……。
  * 你有想过如果让两个区块加载器保持能触发实体复制的条件吗？没错会发生无限的实体复制，这几乎必定卡死你的游戏，在还能操作的时候尽快重启吧。



## 有趣的现象

大部分影响材料的功能都无法在镜像世界正常生效，物质转换不能正常进行，物质吞噬将失效，大部分行为都无法新建材料等等…… 

不过无法正常生效不代表什么用都没有，还是有一些有趣的事情的。

## 镜像世界的代码原理

游戏将地图中的材料称为`Cell`[[3]](#cite_note-3)，一个区块是由 512x512 个单元组成的。 

然后游戏中每个区块都属于一个更大的结构，我们在这里称其为区域[[4]](#cite_note-4)，由于硬编码导致一个区域只能包含 512x512 个区块。 

区域相关伪代码结构如下： 
    
    
    typedef struct Cell (*cell_array)[0x40000];
    struct ChunkMap {
        int unknown[2];
        cell_array* (*cells)[0x40000];
        int unknown2[8];
    };
    struct GridWorld {
        struct GridWorld_vtable* vtable;
        int unknown[318];
        int world_update_count;
        struct ChunkMap chunk_map;//+1280
        int unknown2[41];
        struct GridWorldThreadImpl* mThreadImpl;
    };
    

这里面的`ChunkMap::cells`就是区域的定义。而游戏在运行中只会有一个GridWorld的实例，这使得区域是单例实现的。 

由于单例的问题，这导致游戏不能有两个活跃的区域被加载，这也是为什么游戏在运行中只能加载一个区域大的世界。 

这是游戏判断区块是否加载的伪代码： 
    
    
    bool __thiscall is_chunk_loaded(ChunkMap* this, int x, int y){
        uint16_t offset_x = (uint16_t)(x >> 9);// >> 9 类似 / 512
        offset_x -= 256;
        offset_x &= 0x1FF;
    
        uint16_t offset_y = (uint16_t)(y >> 9);
        offset_y -= 256;
        offset_y &= 0x1FF;
        offset_y *= 512;
        return *this->cells[offset_x + offset_y];
    }
    

可以看到游戏通过`x &= 0x1FF`的形式，屏蔽了大于等于 512 的计算结果防止越界。 

通过以上代码来确定坐标对应的区块，如果区块未加载，那么解引用出来的是空指针 0 ，而 0 代表 false ，游戏认为区块并不处于加载状态。 

反之有区块则不是空指针，那么游戏就认为区块处于加载状态。 

你有发现什么问题吗？nolla完全没有检查坐标是否超出了当前的区域，这使得如果一个坐标过大，那么因为`x &= 0x1FF`，计算结果就会发生**绕回** 现象， 

而0x1FF是 511 ，这让数字限制是 0~511 ，即可以表达 512 个数，那么我们可以算出如果要让计算结果绕回原地的坐标数值是512×512=262144，限制512个数明显是为了防止硬编码的数组越界。 

因为没有进行特殊的处理而是直接使用，导致了镜像世界Bug的诞生。 

游戏在获取区块的指针之后，就通过这个区块进一步获得网格单元也就是材料的信息了。所以地形是共用的。
